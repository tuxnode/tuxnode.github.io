## rCore vs xv6

由于语言的不同，两者在设计思路上也会有区别

### 自定义section

自定义sections绝对是编译/构建工程中的一个绝佳方案，它可以让构建过程脱离对于`Makefile`的依赖，而Rust的理念是通过Cargo来自动化构建

过去对于Makefile强依赖的原因是**地址顺序**，由于kernel离开ROM的时候，pc需要刚好在`0x80000000`上执行`_entry`符号中的代码

这也就意味着在链接的时候，需要在Makefile和链接器脚本进行配合

（如今的xv6已经通过优化链接脚本脱离了对于Makefile的依赖）

![kernel.ld](/rcore/kernel-ld.png)

可以看到已经在`kernel.ld`中显式说明了要先处理`entry.o`，并将其放置到`0x80000000`上

实现了解耦

但是如果在ld脚本中没有显示说明，使用了通用的.text写法，例如：
```text
.text : {
    *(.text .text.*)
}
```

这样就会依赖Makefile中传入`.o`文件的顺序

同时我们可以自己实践查看Rust是如何将函数编译时分为不同section的

```rust
#[inline(never)] // disable inline
pub fn foo() {
    println!("Hello from foo!");
}

#[inline(never)]
pub fn bar() {
    println!("Hello from bar!");
}

fn main() {
    foo();
    bar();
}
```
```bash
rustc --emit=obj main.rs
objdump -h main.o
```

![func-section](/rcore/func-section.png)

这样就可以看到对应的section

总结优势：
> 1. 构建工具解耦，不依赖Unix Makefile
>
> 2. 可以适配LLVM + LTO（链接时优化）
>
> 3. 符合Rust哲学 -> 显示优于隐式

### LLVM and LTO

这个可以单开一个进行讲解

[tsoding](https://www.youtube.com/watch?v=kS_GqDp6IT4)曾聊到`stb`库，也就是`单头文件库`的概念

很多人在这里曾表示过怀疑，认为这种情况只能适用于小型库，但实际上，它可以扩展为任意复杂度

[sqlite](https://www.sqlite.org)值得被称为世界上最伟大的数据库之一，它提供了[amalgamation](https://www.sqlite.org/2026/sqlite-amalgamation-3530400.zip)版本

将所有文件合并为两个`.c`文件

![sqlite](/rcore/sqlite-src.png)

这样做的好处是可以让编译器根据上下文，最大限度地利用编译器优化，也可以实现单头文件调用`sqlite api`

当然缺点是编译速度相对慢

llvm在这里同理，当编译器生成ir后，llvm将所有文件的ir合并在一起，这样就实现了这样的效果

如今结合LTO，使用自定义section可以实现**跨模块函数内联**, **全程序死代码消除**, **虚函数去虚拟化**
