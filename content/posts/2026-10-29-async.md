## TL;DR

很长一段时间里，我用 `tokio::spawn` 都说不出它和 `std::thread::spawn` 到底差在哪。文档只会说「更轻」，轻在哪、轻多少、代价是什么，一个字没有。

这篇是自己补课，结论有点反直觉：协程确实快到离谱，7.8ns 切一次，可它救不了你——每个协程还得占一块栈，而栈才是真正的成本。转折点在于让编译器把状态搬进结构体，「保存现场」从此从切栈退化成一个整数。

```text
线程太贵 → 能不能自己让出 → 让出时保存什么 → 写个协程试试
  → 能跑，但每个协程要一块栈 → 栈能不能不要 → 编译器把状态搬进结构体
    → 谁来反复调用这个结构体 → executor
      → 它怎么知道可以继续了 → waker
        → 谁负责触发 waker → reactor（epoll）
          → 一个核不够 → 多 worker + 本地队列
```

每一节都在回答上一节剩下的问题。卡住的时候往回翻一节，通常就能接上。

## 三个词，三件事

先把话说清楚，这三个词经常被混着用，但它们回答的完全不是一个问题。

| 概念 | 回答什么 | 靠什么 |
|---|---|---|
| 并发 | 同时在推进几个任务 | 程序结构 |
| 并行 | 有几个任务在同一时刻真在跑 | 核的数量 |
| 异步 | 等的时候线程要不要跟着停 | 编程模型 + runtime |

三者互相独立，能随便组合：

- Redis 单线程事件循环：并发 + 异步，不并行。一个核，几万个连接轮流推进。
- 四个线程各算一块矩阵：并行，不必异步。谁也不用等谁。
- 四个线程各自 `read()` 一个 socket：并发 + 并行，但同步。每个线程实打实睡在内核里。
- tokio 默认配置：三样都有。多核跑多个 worker，每个 worker 上多个任务交替推，等待全扔给 epoll。

顺便拆掉一个误解：**异步不等于更快。** 它只是把「等」的成本从「一个线程」压到「一条队列记录」。纯 CPU 的活上异步，只会多出状态机的开销，一点便宜都占不到。

## 线程贵在哪

最朴素的服务器长这样：

```c
while (1) {
    int fd = accept(listen_fd, NULL, NULL);
    pthread_create(&t, NULL, handle, (void *)(intptr_t)fd);  // 一个连接一个线程
}
```

能跑，但撑不住一万个连接。问题不在 `accept`，在于「等待」被绑死在了一个调度实体上：

- 每个线程要一块栈。glibc 默认给 8MB 虚拟地址空间，就算改到 64KB，一万个也是 640MB 起步；
- 每个线程是内核的调度实体，切换要进内核、换页表、刷 TLB；
- 大部分时间这些线程什么都没干，就在 `read()` 里睡着。

实测（12 核）：

| 规模 | 64KB 栈的线程 RSS | 备注 |
|---|---|---|
| 1,000 | 10.1 MB | |
| 10,000 | 84.6 MB | |
| 18,000+ | — | `pthread_create` 开始失败 |

再测切换。两个线程 `mutex` + `condvar` 打乒乓，含 futex 系统调用：

```text
switches=200000 per_switch=1960.3 ns
```

差不多 2µs 一次。这个数里包着系统调用和调度器，不是纯粹的寄存器保存，但它就是「阻塞式等待」的真实单价。

需求就很清楚了：能不能在用户态自己决定让出，别问内核。

## 手写协程

### 让出要保存什么

「暂停一个函数，之后再从原地继续」，翻成机器层面就三样东西：

1. **栈**：局部变量、返回地址都在里面；
2. **`rsp`**：指向栈顶，恢复它等于恢复整条调用链；
3. **callee-saved 寄存器**：`rbx`、`rbp`、`r12`~`r15`。caller-saved 的不用管，切换发生在一次函数调用里，调用者本来就不指望它们活着。

有栈协程的做法因此很直白：给每个协程一块自己的栈。切换时把寄存器压到自己栈上，`rsp` 存进变量，然后把 `rsp` 换成对方的，再把对方的寄存器弹出来。

可以参考这个小示例：[TinyRoutine](https://github.com/tuxnode/TinyRoutine)

### ucontext 版

glibc 有现成接口：

```c
#define N 5000000

static ucontext_t main_ctx, co_ctx;
static char stack[64 * 1024];

static void co_entry(void) {
    for (;;) {
        swapcontext(&co_ctx, &main_ctx);   // 让出
    }
}

int main(void) {
    getcontext(&co_ctx);
    co_ctx.uc_stack.ss_sp   = stack;
    co_ctx.uc_stack.ss_size = sizeof(stack);
    co_ctx.uc_link          = &main_ctx;
    makecontext(&co_ctx, co_entry, 0);

    for (long i = 0; i < N; i++)
        swapcontext(&main_ctx, &co_ctx);   // 恢复
}
```

跑五百万次来回：

```text
per_switch=161.70 ns
```

能用。但比预期慢了一个数量级，这个数不对劲。

### 162ns 花在哪

遇到慢数字，第一反应不该是「换个库」，而是问钱花哪了。手边就两个工具：`strace` 看系统调用，`objdump` 看指令。

先看系统调用：

```text
$ strace -c -e trace=rt_sigprocmask ./ctx2      # 1000 次 swapcontext
% time     seconds  usecs/call     calls    errors syscall
100.00    0.001037           0      2001           rt_sigprocmask
```

1000 次切换，2001 次 `rt_sigprocmask`。每个 `swapcontext` 两次。

再看反汇编，就全明白了：

```asm
0000000000052b00 <swapcontext@@GLIBC_2.2.5>:
   ...
   mov    %rax,0xa8(%rdi)        # 保存返回地址
   lea    0x8(%rsp),%rcx
   mov    %rcx,0xa0(%rdi)        # 保存 rsp
   ...
   fnstenv (%rcx)                # 连 x87 状态都存
   stmxcsr 0x1c0(%rdi)           # 还有 MXCSR
   mov    $0x2,%edi              # SIG_SETMASK
   mov    $0x8,%r10d
   mov    $0xe,%eax              # rt_sigprocmask
   syscall
   ...
   fldenv (%rcx)                 # 恢复 x87 / SSE 状态
   ldmxcsr 0x1c0(%rdx)
   mov    0xa0(%rdx),%rsp
   ...
   ret
```

除了通用寄存器，它还得：

- 存取**信号掩码**，两次系统调用——先 `SIG_BLOCK, NULL` 查当前掩码，再设对方的；
- 存取 **x87 / SSE 的控制状态**，`fnstenv`、`stmxcsr`；
- 走一遍完整的 `ucontext_t`，近 1KB 的字段。

这些东西放在 1970 年代是必要的，协程之间确实该有独立的信号掩码和浮点环境。但你只是想「切一下栈」的时候，全是冤枉钱。

### 七行汇编

把上面那些全删掉，只留最小集合：

```c
__asm__(
"co_switch:\n"
"  push %rbp\n"
"  push %rbx\n"
"  push %r12\n"
"  push %r13\n"
"  push %r14\n"
"  push %r15\n"
"  mov  %rsp, (%rdi)\n"      /* *save_sp = rsp  */
"  mov  %rsi, %rsp\n"        /* rsp = new_sp    */
"  pop  %r15\n"
"  pop  %r14\n"
"  pop  %r13\n"
"  pop  %r12\n"
"  pop  %rbx\n"
"  pop  %rbp\n"
"  ret\n"
);
```

新协程的启动用一个假栈帧糊过去：栈顶压一个返回地址占位，压入口函数地址，再补 6 个 0 冒充「已保存的寄存器」，然后让 `co_switch` 的 `ret` 直接跳进入口函数。

```text
per_switch=7.75 ns
```

7.8 对 162，差 20 倍。差别全在上面那堆「顺手做的事」上。

顺便说一句，协程切换本身几乎不要钱。6 次 `push`、6 次 `pop`、一次 `ret`，比一次普通函数调用贵不了多少。真正贵的东西——系统调用、调度器、缓存失效——这段代码里一个都没有。

| 方式 | 一次切换 | 切换时发生了什么 |
|---|---|---|
| 手写汇编协程 | **7.8 ns** | 12 条指令，不出用户态 |
| `ucontext` | **162 ns** | 上述 + 2 次系统调用 + 浮点环境 |
| 线程 ping-pong | **1960 ns** | 陷入内核、调度器选下一个、可能换页表 |

这张表是理解 async 的起点。**并发的瓶颈从来不是切换，是每个并发单元占多少资源。** 线程贵在栈和内核调度实体，协程贵在……也要一块栈。

### 栈的问题

手写版跑得飞快，但有三个坑绕不过去：

1. **每个协程一块栈**。64KB × 100 万 = 64GB 虚拟内存。而且栈大小得提前猜，猜小了爆栈，猜大了浪费。
2. **栈没法跨暂停点保存**。这条在 Rust 里是致命的：`async fn` 返回 `Pending` 的时候栈帧已经销毁了，函数都返回了，哪来的栈给你存。
3. **跨暂停点的借用没法静态检查**。编译器看到的是一个「中途返回、之后再进来」的函数，它证明不了你手里的 `&mut` 在暂停期间没被别人碰过。

前两条都指向栈。想绕开它，只能换一个存状态的地方。

## tokio：把栈扔掉

### 一个整数记住走到哪

「暂停」不一定非得保存栈。如果**编译器知道哪儿可能暂停**，它就能在编译期把函数切成若干段，每段的局部变量搬进结构体，再用一个整数记「现在到第几段」。

协程于是从「一块栈加一个 `rsp`」变成了「一个小结构体加一个 `match`」。这就是无栈协程。

```rust
// 你写的
async fn fetch(id: u32) -> String {
    let a = step_one(id).await;    // 暂停点 1
    let b = step_two(a).await;     // 暂停点 2
    b
}

// 编译器大致生成的（示意）
enum Fetch {
    Start(u32),
    WaitOne { id: u32, fut: StepOne },
    WaitTwo { a: String, fut: StepTwo },
    Done,
}
```

一次 `poll` 就是从当前变体往下跑，撞到下一个暂停点，返回 `Pending`，顺手把自己改成下一个变体。函数返回了，栈帧没了，状态还活着——因为它压根不在栈上，在堆上那个结构体里。

### 状态机有多大

一个状态机的大小等于它最大的那个状态。实测两种写法：

```rust
// yield_now：构造一个「第一次 poll 返回 Pending」的 future
async fn small() { let _x = 1u64; yield_now().await; }
async fn big()   { let buf = [0u8; 4096]; yield_now().await; println!("{}", buf[0]); }

small=2 bytes, big=4098 bytes
```

`big` 里那个 4096 字节的数组必须活过 `await`，所以被搬进了状态机，future 直接变成 4KB。反过来，不跨 `await` 的话它还待在栈上，future 依然很小。

**`await` 写在哪，决定了内存怎么排。** 这是写 async Rust 最该有的直觉，别的都可以慢慢查文档。

### Future 只问一句

标准库就给了这么一个 trait：

```rust
trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

`Poll` 只有两种结果：`Ready(T)` 或者 `Pending`。

注意这个签名里没有任何「等待」「调度」「线程」的字眼。它只描述一件事：问一次，要么好，要么没好的。

一个已经返回的函数，居然还能被再调一次、从原地接着跑。这事儿靠的是 `Pending` 背后那条契约，比签名重要得多：

> 返回 `Pending` 之前，必须保证将来某个时刻 waker 会被调用。否则这个任务就永远睡死了。

整条 async 链条都建在这条契约上。它把「等」劈成两半：

- **任务侧**：我跑不动了，把 waker 交出去，然后返回；
- **事件侧**：条件满足时，调这个 waker。

中间发生了什么、谁在等、等了多久，`Future` 一概不管。

### 40 行 executor

把契约实现出来，就是一个能跑的 runtime 骨架：

```rust
use std::future::Future;
use std::pin::Pin;
use std::sync::Arc;
use std::task::{Context, Poll, Wake, Waker};

struct Noop;
impl Wake for Noop {
    fn wake(self: Arc<Self>) {}       // 真的 runtime 里：把任务塞回队列 + 叫醒 worker
}

struct YieldNow(bool);
impl Future for YieldNow {
    type Output = ();
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        if self.0 { return Poll::Ready(()); }
        self.0 = true;
        cx.waker().wake_by_ref();      // 「我准备好了」，请再 poll 我一次
        Poll::Pending
    }
}

fn block_on<F: Future>(fut: F) -> F::Output {
    let waker = Waker::from(Arc::new(Noop));
    let mut cx = Context::from_waker(&waker);
    let mut fut = Box::pin(fut);       // 钉在堆上，地址不能变
    loop {
        if let Poll::Ready(v) = fut.as_mut().poll(&mut cx) {
            return v;
        }
    }
}

fn main() {
    let n = 10_000_000;
    block_on(async move {
        for _ in 0..n {
            YieldNow(false).await;     // 每次都返回 Pending，被重新 poll
        }
    });
}
```

量一下空转成本：

```text
polls=10000000 per_poll=8.98 ns
```

9ns 一次 `poll`，跟手写协程的 7.8ns 几乎一个水平。不奇怪：两边干的是同一件事，保存一点状态然后跳走，只不过一边存的是寄存器和 `rsp`，另一边存的是状态机变体和几个字段。

这个 `block_on` 是忙等的，waker 什么都不做，只能靠 `loop` 反复问。真实 runtime 不这么干，它需要 `Waker` 真能把任务叫醒，而这就得有个能挂起线程的机制兜底。

### Waker 是个回调

任务让出之后就消失了。谁能把它叫回来，答案在 `poll` 的签名里——`Context`。

`Waker` 长得像个胖指针：一个数据指针加一张虚表，`clone` / `wake` / `wake_by_ref` / `drop`。用 C 的脑子看，它就是「回调函数 + 上下文」：

```c
struct waker {
    void *data;                                  // 通常是任务对象的指针
    void (*wake)(void *data);                    // 唤醒：把任务塞回队列
    struct waker (*clone)(void *data);           // 引用计数 +1
    void (*drop)(void *data);                    // 引用计数 -1
};
```

非得手写虚表，是因为 `Future` 是泛型的，`poll` 的调用方根本不知道具体类型，但 reactor 拿到 `Waker` 之后必须能凭空唤醒一个任务。`Waker` 就是这个被擦掉类型的回调。

一趟完整的往返长这样：

```text
 任务 A: poll() 发现 socket 没数据
        → 把自己的 waker 登记到 fd 对应的槽位
        → 返回 Pending，任务从队列里消失

 epoll: epoll_wait 醒来，发现 fd 可读
        → 取出该 fd 上登记的 waker
        → waker.wake()：把任务 A 塞回运行队列，unpark 一个 worker

 worker: 从队列取出 A，poll() 继续跑，这次拿到 Ready
```

**「异步」的物理实现就是这条链路。** 不是不用等，是把「等」从线程身上挪到 epoll 的等待队列里，于是一个线程能替上万个 fd 等。

### reactor

同步模型下，一万个连接就是内核里一万个等待队列项，每个绑着一个线程。`epoll` 把这堆东西收进一个实例：

- `epoll_ctl` 注册 fd，告诉内核「这个 fd 的可读可写我要」；
- 一个线程 `epoll_wait`，一次返回一批就绪；
- 事件回来之后，runtime 按 fd 找到登记过的 waker，挨个 `wake`。

定时器也走同一条路。所有 `sleep` 的 deadline 放进一个按时间排序的结构（tokio 用的是哈希时间轮），`epoll_wait` 的超时取最近那个 deadline，醒来把到期的任务批量唤醒。所以 `tokio::time::sleep` 不占线程，只占一个槽位。

有一类 IO 这套机制盖不住：**普通文件**。Linux 上文件的 `read` 永远返回 ready，页缓存要么命中要么缺页，没有「等数据包」这个过程，`epoll` 对它没用。所以 tokio 的文件 IO 实际上是扔给阻塞线程池干的。「异步文件 IO」在 Linux 上本质还是线程，只是藏起来了。

### 多核

单线程 executor 跑满一个核就到头了。要加核，直觉做法是一个全局队列、所有 worker 去抢，但那样每次任务切换都得碰一次全局原子变量，核一多就是瓶颈。

tokio 的思路是散开：

- 每个 worker 有自己的**本地双端队列**，自己产出的任务压本地，取也从本地取；
- 本地空了，去别的 worker 队列的**另一端**偷，一次偷一半，既降频率也降冲突；
- 本地满了，倒一半到全局队列，让闲着的 worker 有活干；
- 每个 worker 还留一个**最近唤醒任务的快捷位**：A 唤醒 B 时，B 直接插到 A 所在 worker 的前面先跑。这对请求-响应型负载特别关键，B 要用的数据大概率还在 A 的 L1/L2 里；
- 没活干的 worker 睡在条件变量上（底层是 futex），来新任务就 `unpark` 一个。

默认线程数等于 CPU 核数。这个选择值得想一想：**IO 密集时靠的不是堆线程，是让每个任务尽快让出。** 线程数超过核数只会多出切换，不会多出吞吐。

### 一百万个任务

这里的数字得跟前面的推理对得上。如果一百万个任务需要一百万个线程，那说明前面某一层还没想通。

```rust
use std::time::Duration;
use tokio::time::sleep;

#[tokio::main]
async fn main() {
    let n: usize = std::env::args().nth(1).unwrap().parse().unwrap();
    for i in 0..n {
        tokio::spawn(async move { sleep(Duration::from_millis(500 + i % 100)).await; });
    }
    sleep(Duration::from_millis(50)).await;    // 等任务都注册完
    println!("tasks={n} threads={} rss={}KB", threads(), rss_kb());
}
```

12 核机器上：

| 任务数 | 线程数 | RSS | 每任务 |
|---|---|---|---|
| 1,000 | 13 | 3.7 MB | ~3.7 KB（被进程基线主导） |
| 10,000 | 13 | 7.0 MB | ~700 B |
| 100,000 | 13 | 41.6 MB | ~416 B |
| 1,000,000 | 13 | 386 MB | ~386 B |

（13 = 12 个 worker + 1 个阻塞在 runtime 上的主线程。）

回头对照上面那张线程表：**任务从 1,000 涨到 1,000,000，内核里的线程数一个都没变。** 省下来的就是每任务一块栈。

但也别高兴太早。386 字节照样是钱，任务对象、状态位、引用计数、队列节点全在里面，一百万个就是 386MB。

所以「async 能开一百万个任务」是真的，「async 免费」是假的。它只是把成本从 8MB 虚拟地址空间压到了几百字节堆内存。

## 自己走一遍

上面每个结论都能用一个小程序验掉。顺序比结论重要：

1. **先量线程**。空线程的栈开销，看 `VmRSS` / `VmSize`；两个线程 ping-pong 一次切换。有了这两个数，「线程重」才不是一句空话。
2. **再写最小协程**。`ucontext` 版先跑通，然后用 6 条 `push`、6 条 `pop` 手写一遍。工具就两个：`strace -c` 看多出来的系统调用，`objdump -d` 看编译器背着你干了什么。
3. **自己写一个 `Future`**。返回一次 `Pending`、再返回 `Ready` 的结构体，加一个忙等的 `block_on`。这一步会逼你想清楚 `Waker` 到底该干嘛。
4. **接上 `epoll`**。一个 fd，`epoll_ctl` 注册，`epoll_wait` 等，事件回来调登记的 waker。做完这一步，手上就是一个不到 100 行的 runtime。
5. **最后再回去看 tokio 文档**。这时候你关心的会从「它是什么」变成「它怎么处理这些边界」：超时、取消、多 worker、阻塞任务。

卡住的地方基本就是理解的缺口，比读十篇综述管用。

## 怎么选

| 场景 | 选择 | 理由 |
|---|---|---|
| 上万连接、IO 为主（网关、代理、IM） | async | 每连接几百字节，等的是网络不是 CPU |
| CPU 密集（编解码、计算） | 线程池 / rayon | async 不加核，还会堵住 executor |
| 少量长任务、逻辑简单 | 线程 | 一个 `join` 就完事，不用引入 runtime |
| 需要超时、取消、组合 | async | `select!` / `timeout` / `drop` 即取消 |
| 需要清晰调用栈调试 | 线程 | async 的 backtrace 是一堆状态机帧 |
| 库作者 | 尽量同步 | async 会传染，把 runtime 选择强加给调用方 |

几个坑，按严重程度排：

1. **在 async 里做阻塞操作**。一次 `std::fs::read` 或者 `sleep` 就能卡死整个 worker 上的所有任务。要么 `spawn_blocking`，要么别在 async 里做。
2. **CPU 密集任务塞进 `tokio::spawn`**。它不会自动分到多核，只会让别的任务饿着。用 `spawn_blocking` 或专门的线程池。
3. **以为 `tokio::spawn` 是并行的**。它是并发；并行度取决于 worker 数量和任务肯不肯让出。
4. **忘了 `Pending` 契约**。手写 `Future` 时返回 `Pending` 却不注册 waker，任务就永久挂起，不报错，只是不动。

## 最后

真正把这几个概念串起来的，是那段 7 行汇编。

协程切换只要 7.8ns，说明「暂停一个函数」本身几乎不要钱；162ns 的 `ucontext` 贵在两次 `rt_sigprocmask`；1960ns 的线程贵在内核调度。tokio 走的是第四条路：干脆不保存栈，让编译器把函数切成状态机。于是切换退化成一次 `poll`，9ns，真正的开销只剩「数据没准备好时那次 `epoll_wait`」。

想通这一层，`async fn` 就不神了。它只是一个被编译器改写过、会在中途返回的结构体。剩下的全是工程问题：谁来 `poll`、谁来 `wake`、几个线程一起 `poll`。

后面还留了两个坑没填：`epoll` 在超高并发下到底卡在哪，是 `epoll_wait` 本身还是事件分发那层的缓存失效；以及 `io_uring` 会不会让「reactor + waker」这套东西变得多余——毕竟它连「通知」都能省掉。
