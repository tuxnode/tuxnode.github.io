## TL;DR

上一篇把 `async fn` 拆成了状态机，末尾留下两个问题：`epoll` 在高并发下的瓶颈位置，以及 `io_uring` 是否会取代 reactor。

本文沿着「等待」这一动作梳理四代 IO 接口。每一代的改动都落在同一组变量上：**由谁挂起、由谁唤醒、以及唤醒之后由谁完成数据搬运。**

```text
阻塞 read：一万条连接对应一万个阻塞线程
  → select/poll：一次等待一批，但每次调用都要重传整个集合
    → epoll：注册一次，内核常驻，只返回就绪项
      → 但 epoll 只声明「现在读取不会阻塞」，数据仍需用户态搬运
        → Linux AIO 试图连搬运一并接管，但仅对 O_DIRECT 有效
          → io_uring：提交队列 + 完成队列，内核完成搬运并回写结果
            → reactor 的职责范围因此缩小，但并未消失
```

结论先行：**epoll 的开销不在扫描，而在唤醒路径和返回后的事件分发**。io_uring 改变的确实是「谁执行系统调用」，但它提供的是**完成（completion）语义**，而 Rust 的 `Future` 是按**就绪（readiness）语义**设计的。两者之间的语义差，是当前所有 Rust io_uring 封装必须处理的核心问题。

## 等待的三个变量

四代接口的差异，可以归结为三个变量的不同取值：

- **挂起**：数据未就绪时，哪个执行单元停下来；
- **唤醒**：条件满足时，由谁通知，通知给谁；
- **搬运**：通知之后，由谁把数据从内核缓冲区复制到用户空间。

| 接口 | 挂起 | 唤醒 | 搬运 |
|---|---|---|---|
| 阻塞 `read` | 线程 | 内核（`wake_up` 等待队列） | 线程，在 `read` 内部 |
| `select`/`poll` | 线程 | 内核 | 线程，另一次 `read` |
| `epoll` | 线程（`epoll_wait` 内） | 内核回调 | 线程，另一次 `read` |
| `io_uring` | 线程（可选） | 内核写 CQE | **内核** |

前三代的共同点是：内核只负责声明「已就绪」，真正的 `read()` 仍由用户态发起。这并非设计疏漏，而是接口形状决定的——`read(fd, buf, n)` 的 `buf` 是用户态地址，内核只在调用发生的那一刻才知道它。

io_uring 的核心机制，就是把 `buf` 的地址在操作发起时提前交给内核。

## 阻塞 IO：等待绑定在线程上

> **机制**：阻塞 `read` 在数据未就绪时，会把当前线程挂入该 fd 的等待队列并让出 CPU。

```c
ssize_t n = read(fd, buf, len);
```

数据未到达时，内核依次执行：

1. 将线程挂到 fd 对应的 `wait_queue_head_t` 上；
2. 将线程状态置为 `TASK_INTERRUPTIBLE`，调用 `schedule()` 让出 CPU；
3. 调度器选择下一个可运行任务；
4. 数据到达后，网卡中断进入软中断，协议栈调用 `wake_up()` 将线程置回 `TASK_RUNNING`；
5. 线程被重新调度，从 `schedule()` 返回，复查条件后执行拷贝。

上一篇测得线程 ping-pong 一次约 1960ns，成本即来自这一路径：**挂起和唤醒各一次内核陷入，中间还要经过调度器**。

一万条连接意味着一万份这样的结构。真正的代价不是切换延迟，而是**每份等待都占用一个完整的调度实体和一块栈**：为了等待一个几百字节的数据包，付出的是 8MB 虚拟地址空间。

## select 与 poll：等待绑定在集合上

> **约束**：内核必须知道调用方正在等待哪些 fd。`select`/`poll` 的答案是把集合随每次调用传入。

```c
fd_set rfds;
FD_ZERO(&rfds);
FD_SET(fd, &rfds);
select(maxfd + 1, &rfds, NULL, NULL, NULL);
```

这一设计有三个固有缺陷：

- `fd_set` 是位图，容量由 `FD_SETSIZE` 固定为 1024，fd 号超出即无法表示；
- 每次调用都要将整个位图从用户态复制进内核，返回时再复制回来。一万个 fd 对应每次 1250 字节的往返拷贝，与就绪数量无关；
- 内核不保存「谁在等」的状态，每次调用都必须从头扫描。

`poll` 将位图换成数组，取消了 1024 上限，但另外两条依然存在：**每次重传全部、每次内核全扫**。

复杂度为 O(n)，且 n 是注册的 fd 总数，而非就绪数量。一万个连接中只有三个活跃，仍需扫描一万次。

`select`/`poll` 把「注册」与「等待」压缩在同一个系统调用里，这一耦合直接导致全量重传。将注册拆分为独立操作、由内核常驻保存，是下一步的必然方向。

## epoll：等待搬进内核常驻结构

`epoll` 的做法是**把「谁在等」从一次调用的参数，变成内核中的长期对象**。

```c
int ep = epoll_create1(0);

struct epoll_event ev = { .events = EPOLLIN, .data.fd = fd };
epoll_ctl(ep, EPOLL_CTL_ADD, fd, &ev);        // 注册一次，长期有效

struct epoll_event evs[64];
int n = epoll_wait(ep, evs, 64, -1);          // 仅返回就绪项
```

### 内部结构

- 一棵**红黑树**保存所有已注册 fd，支撑 `epoll_ctl` 的 O(log n) 增删改查；
- 一个**就绪链表**保存已就绪、尚未被取走的项。

注册时，内核在该 fd 的等待队列上挂一个回调 `ep_poll_callback`。fd 一旦被标记为就绪，回调触发，将对应节点链入就绪链表。

`epoll_wait` 因此只做两件事：链表非空则取走一批；否则睡在 epoll 自身的等待队列上。复杂度为 O(就绪数)，与总连接数无关。一万个连接、三个活跃时，`epoll_wait` 只处理三个。

### 成本没有消失，只是转移

上一篇留下的问题是：epoll 在高并发下的瓶颈是 `epoll_wait` 本身，还是事件分发层的缓存失效。答案是后者。`epoll_wait` 自身开销很低，代价集中在它周围的两段路径上。

完整往返如下：

```text
网卡中断（CPU 0）
  → 软中断 → 协议栈 → 数据进入 socket 接收队列
  → ep_poll_callback()：获取 ep->lock，将节点挂入 rdllist
  → wake_up() 唤醒 epoll 的等待者（可能触发 IPI 到另一核）

worker（CPU 3）
  → 从 epoll_wait 返回，复制就绪事件到用户态
  → 遍历事件数组：fd → runtime 中登记的对象 → 取出 waker
  → waker.wake()：将任务推入某个 worker 的本地队列
  → 任务被调度，poll 一次，返回 Ready，再调用 read() 复制数据
```

中断发生在 CPU 0、处理在 CPU 3，中间至少涉及两次缓存行所有权转移（`rdllist` 的 head/tail、任务的队列节点）。这些开销不出现在 `epoll_wait` 的返回值中，但构成真实的性能成本。

另一处开销更隐蔽：`rdllist` 与 `ep->lock` 都是**每个 epoll 实例一份**。多线程共享单个实例时，所有 worker 竞争同一把锁；每个 worker 各持一个实例时，同一个 fd 只能注册在其中一个实例上，负载不均即出现空转（这也是 SO_REUSEPORT 被广泛采用的原因之一）。

### 就绪语义与完成语义

这一点决定了上层接口的形状，需要单独说明：

> `epoll` 声明的是**「此刻发起一次 `read` 不会阻塞」**，而非**「数据已在用户空间」**。

两者在边界情况下会分离。「就绪」与「真正调用 `read`」之间隔着整个用户态，另一个线程完全可能先一步读走数据。因此在 epoll 上实现异步 IO，`read` 必须能够处理 `EAGAIN`。

epoll 默认为水平触发，条件持续成立时会重复上报，遗漏一次仍有下一次机会，但语义上仍然是「就绪」而非「完成」。这一区别在讨论 io_uring 时将成为关键。

> **遗留问题**：epoll 解决了通知，但数据搬运和每次操作的系统调用仍由用户态承担。

具体有两项：

1. **搬运仍需用户态参与**。一次唤醒后紧跟一次 `read` 系统调用，再加一次内存拷贝，三个动作都无法省略。
2. **每次操作仍是一次系统调用**。一万个就绪事件对应一万次 `read`。

## io_uring：把执行也交给内核

### 它真正取代的是 Linux AIO

io_uring 常被视作 epoll 的替代品，但它最先取代的是 **Linux AIO**（`io_submit` / `io_getevents`）。

Linux AIO 有两处硬伤：

- **仅对 `O_DIRECT` 的块设备真正异步**。走页缓存的文件会在提交阶段同步阻塞。这是上一篇指出「tokio 的文件 IO 实际上是阻塞线程池」的原因——在 io_uring 之前，Linux 没有通用的异步文件 IO。
- **提交与获取完成各一次系统调用**，批量能力有限。

此外，它与 epoll 同属就绪思路的延伸，并未改变「谁搬运数据」。

### 两个环

io_uring 对外只有三个系统调用，核心机制是**用共享内存充当队列，使用户态与内核态直接传递消息，从而绕开系统调用**。

```text
        用户态                        内核态
   ┌──────────────┐            ┌──────────────┐
   │  SQ: tail ───┼─── 写入 SQE ─→│             │
   │  SQ: head ←──┼────────────┼── 消费       │
   ├──────────────┤            ├──────────────┤
   │  CQ: tail ←──┼────────────┼── 写入 CQE   │
   │  CQ: head ───┼─── 读取 CQE ─→│             │
   └──────────────┘            └──────────────┘
        （两块环位于同一段 mmap，SINGLE_MMAP）
```

- **SQ（Submission Queue）**：用户态写入待执行操作，每条 SQE 64 字节；
- **CQ（Completion Queue）**：内核写入执行结果，每条 CQE 16 字节；
- 两侧各自维护 head/tail，通过内存序同步，不使用锁（单生产者/单消费者）。

关键点在于：**填写 SQE 不是系统调用，只是向共享内存写入 64 字节。**

进入内核的时机是推进 `tail`、告知内核有新工作时。一次 `io_uring_enter` 可以：

- 批量提交（`to_submit`）；
- 同时等待批量完成（`min_complete` + `IORING_ENTER_GETEVENTS`）；
- 或仅提交，不等待。

若启用 `IORING_SETUP_SQPOLL`，内核会启动一个线程轮询 `tail`，连这次 `enter` 也可省略，代价是常驻一个核。

### 最小实现

不依赖 `liburing`，直接基于 `linux/io_uring.h` 实现一遍，可以看清封装层所做的工作。

系统调用入口：

```c
#include <linux/io_uring.h>
#include <sys/syscall.h>
#include <sys/mman.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>

static int io_uring_setup(unsigned entries, struct io_uring_params *p) {
    return syscall(__NR_io_uring_setup, entries, p);
}

static int io_uring_enter(int fd, unsigned submit, unsigned wait, unsigned flags) {
    return syscall(__NR_io_uring_enter, fd, submit, wait, flags, NULL, 0);
}
```

初始化阶段最多三次 `mmap`，获得八个指针：

```c
struct ring {
    unsigned *sq_head, *sq_tail, *sq_mask, *sq_array;
    unsigned sq_entries;
    unsigned pending;          /* 已填写、尚未通知内核的 SQE 数 */
    struct io_uring_sqe *sqes;
    unsigned *cq_head, *cq_tail, *cq_mask;
    struct io_uring_cqe *cqes;
    int fd;
};

static void ring_init(struct ring *r, unsigned entries) {
    struct io_uring_params p;
    memset(&p, 0, sizeof(p));
    r->fd = io_uring_setup(entries, &p);
    if (r->fd < 0) { perror("io_uring_setup"); exit(1); }
    r->sq_entries = p.sq_entries;
    r->pending = 0;

    /* 环中承载 SQE / CQE 的区域，外加 array 映射表 */
    size_t sq_sz = p.sq_off.array + p.sq_entries * sizeof(unsigned);
    size_t cq_sz = p.cq_off.cqes + p.cq_entries * sizeof(struct io_uring_cqe);

    /* SINGLE_MMAP：SQ 环与 CQ 环位于同一块物理页，映射一次即可 */
    size_t sz = sq_sz > cq_sz ? sq_sz : cq_sz;
    char *sq = mmap(NULL, sz, PROT_READ | PROT_WRITE,
                    MAP_SHARED | MAP_POPULATE, r->fd, IORING_OFF_SQ_RING);
    char *cq = (p.features & IORING_FEAT_SINGLE_MMAP)
             ? sq
             : mmap(NULL, cq_sz, PROT_READ | PROT_WRITE,
                    MAP_SHARED | MAP_POPULATE, r->fd, IORING_OFF_CQ_RING);

    /* SQE 为定长 64 字节的连续数组，单独映射 */
    r->sqes = mmap(NULL, p.sq_entries * sizeof(struct io_uring_sqe),
                   PROT_READ | PROT_WRITE, MAP_SHARED | MAP_POPULATE,
                   r->fd, IORING_OFF_SQES);

    /* 偏移量由内核给出，不可写死 —— 结构布局可能随版本变化 */
    r->sq_head  = (unsigned *)(sq + p.sq_off.head);
    r->sq_tail  = (unsigned *)(sq + p.sq_off.tail);
    r->sq_mask  = (unsigned *)(sq + p.sq_off.ring_mask);
    r->sq_array = (unsigned *)(sq + p.sq_off.array);

    r->cq_head = (unsigned *)(cq + p.cq_off.head);
    r->cq_tail = (unsigned *)(cq + p.cq_off.tail);
    r->cq_mask = (unsigned *)(cq + p.cq_off.ring_mask);
    r->cqes    = (struct io_uring_cqe *)(cq + p.cq_off.cqes);
}
```

`ring_mask` 的用途来自一个约定：环大小会被向上取整到 2 的幂，于是 `tail & mask` 即为下标，无需取模。两个环因此宁可保留少量冗余空间，也要维持 2 的幂。

填写并提交 SQE：

```c
static struct io_uring_sqe *get_sqe(struct ring *r) {
    unsigned tail = *r->sq_tail + r->pending;      /* 用户态维护逻辑 tail */
    if (tail - *r->sq_head >= r->sq_entries) return NULL;   /* 环已满 */
    unsigned idx = tail & *r->sq_mask;
    r->sq_array[idx] = idx;                 /* array 决定内核的读取顺序 */
    r->pending++;
    return &r->sqes[idx];
}

static void submit_and_wait(struct ring *r, unsigned wait) {
    /* 所有 SQE 填写完毕后，才将 tail 写回共享内存 */
    __atomic_store_n(r->sq_tail, *r->sq_tail + r->pending, __ATOMIC_RELEASE);
    io_uring_enter(r->fd, r->pending, wait, IORING_ENTER_GETEVENTS);
    r->pending = 0;
}
```

主流程：

```c
int main(void) {
    struct ring r;
    ring_init(&r, 8);

    int fd = open("/etc/hostname", O_RDONLY);
    static char buf[256];

    /* 第一条：NOP，用于验证环的连通性 */
    struct io_uring_sqe *sqe = get_sqe(&r);
    memset(sqe, 0, sizeof(*sqe));
    sqe->opcode    = IORING_OP_NOP;
    sqe->user_data = 1;

    /* 第二条：READ，buf 的地址直接交给内核 */
    sqe = get_sqe(&r);
    memset(sqe, 0, sizeof(*sqe));
    sqe->opcode    = IORING_OP_READ;
    sqe->fd        = fd;
    sqe->addr      = (unsigned long)buf;
    sqe->len       = sizeof(buf);
    sqe->off       = 0;
    sqe->user_data = 2;

    submit_and_wait(&r, 1);   /* 两条均提交，但只等待一条完成 */

    /* 收取 CQE。完成顺序不保证与提交顺序一致，需依靠 user_data 认领 */
    for (int got = 0; got < 2; got++) {
        while (*r.cq_head == *r.cq_tail) {          /* 完整实现需处理等待逻辑 */
            io_uring_enter(r.fd, 0, 1, IORING_ENTER_GETEVENTS);
        }
        struct io_uring_cqe *cqe = &r.cqes[*r.cq_head & *r.cq_mask];
        printf("user_data=%llu res=%d\n",
               (unsigned long long)cqe->user_data, cqe->res);
        (*r.cq_head)++;                              /* 通知内核：该项已取走 */
    }
    return 0;
}
```

这段代码在本机编译运行，输出为 `user_data=1 res=0` 与 `user_data=2 res=5`。

几个必须注意的细节：

- **`user_data` 是唯一的身份标识**。64 位整数由内核原样带回。在 Rust 实现中，它通常是 slab 下标或 `Arc<Task>` 的裸指针，CQE 返回时据此定位对应的 waker。这是 epoll 中 `epoll_event.data` 的等价物。
- **完成是乱序的**。两条 SQE 的提交顺序是 NOP、READ，CQE 的返回顺序不作保证，`user_data` 是必需项而非便利项。
- **`res` 即返回值**，负值表示 `-errno`，此处不存在 `errno`。
- **`tail` 必须在用户态先记账**。直接递增共享内存中的 `sq_tail` 会破坏 SQE 的归属：两次 `get_sqe` 返回同一下标，后填的 SQE 覆盖先填的，实际提交出去的是两条相同请求。原因是 `sq_tail` 一旦写入共享内存，即表示该区间可被内核消费，而 `SQPOLL` 模式下内核线程会持续轮询它。正确做法是在用户态维护 pending 计数，仅在提交时写回，liburing 的处理方式与此一致。
- **共用一块 mmap 表明 SQ 与 CQ 生命周期完全一致**。这是接口设计上的信号：提交与完成是一体两面，不像 epoll 的注册表与就绪链表那样可以独立看待。

### 内存开销

以 512 项的环为例：

```text
SQE  : 512 × 64B  = 32 KB
array: 512 ×  4B  =  2 KB
CQE  : 1024 × 16B = 16 KB     （CQ 默认为 SQ 的两倍，用于防止完成事件丢失）
                   ─────────
                    50 KB      ≈ 每条约 100 字节
```

上一篇把「每个并发单元」的成本从 8MB 压缩到几百字节。此处换一个维度：**每条在途 IO 约 100 字节，且其中不含栈、不含调度实体、不含阻塞线程。**

CQ 取 SQ 两倍并非出于冗余考虑，而是因为**完成可能早于提交被消费**。若 CQ 已满仍有 CQE 待写，内核只能置 `overflow` 标志暂存事件，待空间释放后补写。这是一条必须处理的错误路径。

### link 与 multishot

这两个特性在后文讨论 Rust 时会用到：

**link**：为 SQE 设置 `IOSQE_IO_LINK` 后，内核串行执行，任一失败则后续一并取消。`read → write` 这类「把 A 的内容搬到 B」不再需要用户态介入两次。

**multishot**：一条 `IORING_OP_ACCEPT_MULTISHOT` 或 `RECV_MULTISHOT` 会产生**多条** CQE，直至被显式取消。

后者值得注意：**它把就绪语义重新引入了完成接口。** 一次提交、反复完成，正是 `epoll_ctl` 注册一次、反复上报的行为模式，区别在于数据搬运也已并入内核路径。

## 回到 Rust：Future 与两种语义

> **冲突点**：io_uring 提供完成语义，而 `Future::poll` 表达的是就绪语义。

`Future::poll` 只回答一件事：**当前是否完成**。返回 `Pending` 时附有一条契约：**必须保证将来会有调用方触发 `waker`**。

这一语义与 readiness 完全同构：「尚未完成」等价于「条件未满足」，等价于「满足后再询问」。这并非巧合——`Future` 的抽象边界正好落在通知环节，不涉及数据搬运。

三种后端在 Rust 中的接口形状由此分化：

| 后端 | `poll` 返回 `Ready` 的含义 | 借用检查器看到的状态 |
|---|---|---|
| `epoll` | 此刻 `read` 不会阻塞 | 借用仅存在于 `poll` 内部，可使用 `&mut [u8]` |
| 阻塞线程池 | 数据已完成读取 | 同上（阻塞发生在其他线程） |
| `io_uring` | 内核已完成读取 | buffer 由内核持有，**不可访问** |

第三行是全部复杂度的来源。

### reactor 结构不变，事件源改变

epoll 后端的链路：

```text
任务 poll → 收到 EAGAIN → 将 waker 登记到 fd 对应槽位 → 返回 Pending
epoll_wait 返回 → fd 就绪 → 取出 waker → wake() → 任务重新入队
任务 poll → 本次 read 成功 → 返回 Ready
```

io_uring 后端：

```text
任务 poll → 填写一条 SQE（user_data = 任务 id）→ 返回 Pending
CQE 返回 → 按 user_data 定位 waker → wake()
任务 poll → 直接读取 cqe->res → 返回 Ready
```

**结构完全一致**，差异仅在事件源：由「fd 就绪」变为「CQE 到达」。因此成本最低的接法是复用现有 epoll reactor——io_uring 的 fd 可被 poll，CQ 中存在事件时即为可读。

代价是：**省下的 `read` 系统调用，被一次 `epoll_wait` 换了回来**。这正是 `tokio-uring` 不采用该方案、而是启动独立线程阻塞在 `io_uring_enter` 上的原因。

### buffer 所有权与借用

核心差异体现在签名上：

```rust
// tokio（readiness）：借用
async fn read(&mut self, buf: &mut [u8]) -> io::Result<usize>;

// tokio-uring（completion）：移交所有权
async fn read<T: IoBufMut>(&mut self, buf: T) -> BufResult<usize, T>;
```

tokio 可以借用，因为它采用就绪模型：**`poll` 返回 `Ready` 的那一刻，数据已经被 `read()` 复制进 buffer，借用从未跨越暂停点。**

tokio-uring 必须取得所有权，因为 `poll` 返回 `Pending` 时，`buf.as_mut_ptr()` 已经交给内核，**内核可在其后的任意时刻向该地址写入**。此时若用户态仍持有 `&mut [u8]`，即构成 data race，且是由内核参与、编译器无法覆盖的 race。

这也解释了 `Pin` 在此处的性质变化：

> 在 `async fn` 的状态机中，buffer 是结构体的一个字段，其地址等于 future 地址加固定偏移。**因此 `Pin` 住 future，等价于固定住交给内核的那个指针。**

在 epoll 下，`Pin` 主要用于防止自引用状态机被移动；在 io_uring 下，它还承担第二重职责：**保证内核持有的裸指针不会失效**。同一类型，两种用途。

取消操作同样受到影响。就绪语义下，取消即停止 `poll`。完成语义下，取消需要发出 `IORING_OP_ASYNC_CANCEL` 并**等待其结果**，因为取消发出之前该操作可能已经完成。在 CQE 返回前释放 buffer，内核就会写入已释放的内存。

这解释了 Rust 中所有 io_uring 封装的共同特征：`Drop` 中带 grace period、返回 `BufResult`、不提供 `&mut [u8]` 接口。这些并非设计缺陷，而是完成语义的必然结果。

### 内核承担了部分 executor 职责

结合前两个特性：

- **link**：将「两个 await」压缩为「一条 SQE 链」，用户态状态机减少一个变体，减少一次唤醒；
- **multishot**：将「`epoll_ctl` 注册 + 反复 `wake`」的模式并入内核。

内核确实开始承担原本属于 reactor 与 executor 的部分职责，但这不构成对 `Future` 的替代。内核交付的粒度是「一批操作已完成」，`Future` 表达的粒度是**一个任务的生命周期**：

- 组合：`select!` / `join!` / `timeout` 在类型层面完成组合，内核不区分 future 与任务的归属关系；
- 取消：`drop` 即取消，这一语义只能由用户态定义，内核只识别 SQE；
- 调度：任务间的公平性、队列、偷取策略，内核不参与；
- 抽象：同一份代码需要在 epoll 与 io_uring 上运行，就需要一层将「完成」适配为「就绪」的中间层，即 reactor。

**内核优化的是单次系统调用的往返成本，Future 优化的是逻辑任务的表达粒度。两者层级不同，不存在替代关系。**

## 工程约束与现实问题

io_uring 目前面临的主要障碍是**攻击面**。

一个能在内核中长期持有用户指针、文件引用，并允许注册任意内存区域作为 buffer 的接口，等于在内核中引入一整套新的生命周期管理逻辑。历史问题主要集中在这几个方向：注册 buffer 与文件表的管理、SQE 链的失败回滚、各 opcode 的参数校验。

由此产生三类现实约束：

- **部署受限**。Google 在 Android 上对第三方应用禁用了 `io_uring`，ChromeOS 与内部生产环境同样关闭。官方给出的理由是其在提权漏洞中出现频率过高，收益不足以覆盖风险。此外，部分容器运行时与发行版在 seccomp 中拦截 `io_uring_setup`，云厂商也可能在宿主机层面禁用，导致代码在目标环境直接返回 `EPERM`。
- **工具链不成熟**。`strace` 只能观察到一次 `io_uring_enter`，具体提交内容位于共享内存中，不进入内核便无法观察。排查问题时既没有 `read` 那样的调用栈，也没有 epoll 那样直接的 fd 语义。
- **性能收益有条件**。小 IO 场景下，填写 SQE 与收取 CQE 的开销未必低于一次 `read`。`SQPOLL` 需要常驻一个核，`IOPOLL` 仅对块设备有意义（绕开中断，纯轮询）。网络路径的主要成本通常是协议栈与内存拷贝，而非系统调用次数，批处理收益要在高 IOPS 下才会显现。

其定位因此比较明确：**不是通用替代方案，而是面向特定负载的工具**。

## 选型

| 场景 | 选择 | 理由 |
|---|---|---|
| 普通网络服务，连接数万级 | `epoll`（tokio） | 生态成熟、可观测性好、不依赖内核配置 |
| 极高 IOPS、大量小请求 | `io_uring` | 批处理提交，可省去逐次系统调用 |
| 真正的异步文件 IO | `io_uring` | Linux 上无其他方案，其余实现均为线程池封装 |
| 需要面向任意客户端分发 | `epoll` | 目标环境可能不具备 `io_uring` 权限 |
| 延迟敏感、需要掌控调度 | `io_uring` + 自研 executor | `SQPOLL` 加绑核 |

常见错误：

1. **假设 epoll 上报可读即可读到数据**。必须处理 `EAGAIN`，多线程共享 fd 时尤其如此。
2. **使用边缘触发但未排空**。ET 只在状态跳变时上报一次，不读取至 `EAGAIN` 将不再收到通知。
3. **假设 io_uring 的完成顺序与提交顺序一致**。`user_data` 是必需项。
4. **在取消后立即释放 buffer**。取消是异步操作，CQE 可能在释放之后到达。
5. **为 completion 后端设计 `&mut [u8]` 接口**。编译器会拦截，不应绕过。

## End

本文承接上一篇的结尾。当时留下的两个问题现已可以回答。

`epoll` 的瓶颈确实不在 `epoll_wait` 的返回值中，而在中断上下文里的 `ep_poll_callback`、跨核的 `rdllist` 争用，以及返回之后「fd → waker → 队列 → 调度」的分发路径。**扫描早已不是问题；问题在于把一万个等待合并进内核之后，仍须将它们逐一拆解出来。**

io_uring 不会使 reactor 变得多余，但改变了它的形态。epoll 的 reactor 将就绪事件翻译为唤醒，io_uring 的 reactor 将完成事件翻译为唤醒。**翻译层始终存在，变化的只是源语义：从「可以了」变为「做完了」。**

真正被改变的是 Rust 侧：**borrow checker、`Pin`、`Drop` 三者的含义，都随「谁持有 buffer」一并改变。** 接口从就绪切换到完成，表面上是内核层面的改动，实际上重划了 Rust 内存安全模型的边界。

后续值得继续梳理的方向是 `IORING_REGISTER_PBUF_RING`（预注册 buffer 环）与 zero-copy 收发。那条路径才能真正消除拷贝，但 buffer 生命周期的复杂度会显著上升。
